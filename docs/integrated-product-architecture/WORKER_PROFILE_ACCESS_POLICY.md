# Worker Profile Access Policy

This document defines the canonical access policy for the integrated `WorkerProfile` / `TalentProfile` experience in Rinjani 2.0.

It intentionally **preserves the existing 4-tier edit policy** from the Portal employee-profile PRD and **extends the view policy** into a single matrix that can be applied across:

- Portal `My Profile`
- Portal admin employee directory / employee profile
- Talent `My Team`
- Talent Pool
- Succession Planning
- Talent Committee Portal
- Profile export (`PDF` / `XLSX`)

## Purpose

After the Worker Profile rollout, profile behavior must be consistent regardless of where a profile is opened. The same employee can be viewed in different contexts, but section visibility, field masking, edit affordances, and export payloads must still follow one shared policy.

This document separates two decisions that must not be conflated:

- **Edit policy**: whether a field can be edited, and under what workflow.
- **View policy**: whether a field/section can be seen, masked, hidden, or exported for a given viewer and access context.

## Policy Layers

Every profile field/section must be evaluated in this order:

1. **Edit Tier**: determines editability workflow.
2. **Sensitivity**: determines how strict the view/export policy must be.
3. **Viewer Role**: determines who the viewer is in the organization.
4. **Access Context**: determines why the profile is being opened.
5. **Output Surface**: determines whether the same data is being rendered on-screen or exported.

## 1. Edit Policy: Existing 4 Tiers

The integrated profile must continue using the existing 4-tier categorization exactly as the edit-policy foundation.

### Tier 1 — Immutable / Sync Only

Definition:

- System of record is HRIS, LMS, DWH, or another upstream system.
- No manual edit in Rinjani.
- Any refresh happens by synchronization.

Behavior:

- UI state: `read-only`
- No inline edit affordance
- No admin direct edit in profile UI
- Display source label such as `DWH Generated`, `API`, or equivalent sync source

Typical examples:

- Employee master identity
- Employment status and organization structure
- Position history
- Performance history
- Learning history
- Contract data

### Tier 2 — Approval Required

Definition:

- User-initiated change is allowed, but the data is legally, financially, or operationally sensitive.
- Change must be routed through approval workflow with support documents where needed.

Behavior:

- UI state: `editable_with_approval`
- User submits change request, not direct mutation
- Attachment support required when applicable
- Approval status and audit trail visible

Typical examples:

- Family members for benefits
- Education and certification records that change official qualification
- Legal identification changes
- Sensitive contact/benefit records where the PRD explicitly requires approval

### Tier 3 — Direct Update / Self Service

Definition:

- User can update directly without admin approval.
- Data is low-risk and non-legal, but must still be auditable.

Behavior:

- UI state: `editable_direct`
- Inline edit allowed
- Save applies immediately
- Audit trail still recorded

Typical examples:

- Private contact details
- Alias / personal preferences
- Low-risk descriptive notes
- Some contribution / non-legal profile enrichments

### Tier 4 — Rinjani Produced / Engine Result

Definition:

- Data is generated by Rinjani analytics, scoring, or talent engines.
- It is not edited as profile master data.

Behavior:

- UI state: `read-only_generated`
- Not editable from profile
- May be highly sensitive for viewing even though it is read-only

Typical examples:

- Career aspiration summary
- EQS score and breakdown
- 9-box classification
- Talent pool status
- Calibration result

## 2. Section Model

The canonical profile is divided into these top-level sections:

- `Core CV`
- `Talent Insights`
- `Performance Insights`
- `Governance History`
- `Export View`

### Core CV

Typical contents:

- Personal information
- Employment information
- Education
- Family
- Language skills
- Work / assignment history
- Learning history
- Contributions and achievements

### Talent Insights

Typical contents:

- EQS and breakdown
- 9-box / talent cluster
- Talent pool data
- Career aspiration summary
- IDP summary
- 360 assessment summary
- Job tender / mobility summary
- Succession summary

### Performance Insights

Typical contents:

- Performance history summary
- Latest final PI / rating
- Planning portfolio summary
- Monitoring status summary
- Manager/admin team KPI summary where relevant

### Governance History

Typical contents:

- Talent review proposals
- HC recommendations
- TC decisions
- Calibration detail / committee outcome
- Approval notes
- Governance references that are not for broad employee consumption

## 3. Sensitivity Classes

The existing documents imply different sensitivity levels. For integrated implementation, all profile fields/sections must also map to one of these sensitivity classes.

### S0 — Basic

Low sensitivity. Normal profile data that is broadly safe for permitted viewers.

Examples:

- Name
- Position title
- Organization
- Education summary
- Public-facing achievements

### S1 — Internal Personal

Personal data that is still legitimate for profile viewing, but should not be exposed beyond expected internal viewers.

Examples:

- Private email
- Personal phone
- Address
- Family details
- Health-related records

### S2 — Talent / Performance Sensitive

Talent and performance information that should not be visible broadly across the organization.

Examples:

- EQS components
- Performance scores
- Talent pool ranking
- Risk profile
- Readiness labels
- Team-performance summaries

### S3 — Governance Restricted

Most sensitive information. Only visible in governance or authorized admin contexts.

Examples:

- HC recommendation details
- TC rationale
- Committee decision history
- Calibration notes
- Approval notes and governance-only references

## 4. Viewer Roles

These roles are the canonical access-policy roles for integrated implementation.

### `employee`

- Default worker viewing their own profile.
- Can always access self profile.
- No governance history by default.

### `manager`

- Line manager viewing a direct or explicitly authorized subordinate.
- Can access relevant team-facing talent/performance summaries.
- No unrestricted governance history.

### `hc_admin`

- HR / HC operations or business partner role handling workforce data and approval workflows.
- Broad access to core profile and operational summaries.
- Governance visibility depends on whether the admin is acting in governance context.

### `talent_admin`

- Talent management operator role.
- Broad access to talent and succession surfaces.
- Governance visibility allowed where needed for talent operations, but not automatically identical to committee view.

### `talent_committee`

- Committee or governance reviewer.
- Access to governance history and sensitive committee-facing insight in committee context.

### `portal_admin`

- Portal-level admin or support role.
- Access to employee directory and core employee profile.
- Does **not** automatically inherit governance-restricted visibility.

## 5. Access Contexts

The same role can have different visibility depending on why the profile is opened.

### `self`

- Employee opens own profile via `My Profile` or `My Talent Home`.

### `manager`

- Manager opens a direct or authorized report via team workflow.

### `talent_pool`

- Viewer opens a profile from Talent Pool candidate exploration.

### `succession`

- Viewer opens a profile from succession workflow.

### `committee`

- Viewer opens a profile during committee/review discussion.

### `portal_admin`

- Viewer opens a profile from Portal employee directory or admin employee search.

## 7. Detailed View Rules by Section

### Core CV

Default rule:

- Always available to the employee on self view.
- Available to managers/admins only as needed for legitimate work context.

Field handling:

- S0 fields: visible to all authorized viewers
- S1 fields: employee sees full value; managers/admins see only when operationally justified
- S1 health/disability data: hidden by default outside explicit HR operational need

### Talent Insights

Default rule:

- Employee can see own talent summary.
- Manager can see subordinate talent summary relevant to people management.
- Talent roles can see full talent insight.
- Portal admin sees only filtered summary, not full governance-grade detail.

Filtering examples:

- `employee/self`: show own EQS, own aspiration summary, own IDP summary, own talent pool status if already surfaced by product
- `manager/manager`: show subordinate EQS band/score, cluster, IDP status, aspiration coverage, risk summary
- `portal_admin/portal_admin`: show only limited summary where needed; do not show committee-only rationale or raw governance notes

### Performance Insights

Default rule:

- Employee sees own performance summary and KPI summary.
- Manager sees subordinate summary relevant to planning/monitoring/review.
- Portal admin sees only filtered summary, not all operational queues or detailed evidence trails.

Filtering examples:

- show latest rating / PI summary
- show planning portfolio status
- show monitoring status summary
- do **not** surface detailed monthly realization evidence or approval queue contents in profile

### Governance History

Default rule:

- Hidden by default.
- Only visible in governance-oriented contexts to authorized governance roles.

Visible examples:

- `talent_committee` in `committee` context
- `talent_admin` in succession / review contexts where governance work requires it

Hidden examples:

- employee self view
- manager team view by default
- portal admin directory view

## 8. Export Policy

Exports must use the same filtered payload as on-screen rendering. Export cannot elevate access.

### Export Presets

Initial presets:

- `CV Ringkas`
- `Talent Profile Summary`
- `Admin Review Pack`

### Export Rules

- If a section is hidden on-screen for the current viewer/context, it must not appear in export.
- If a field is masked on-screen, export must either mask it the same way or omit it.
- `includeSensitiveFields=true` is only advisory; it cannot override access policy.
- `Governance History` is exportable only for governance-authorized viewers in governance-authorized contexts.

### Format Rules

- `PDF`: presentation / reading oriented
- `XLSX`: analysis / audit working file

Both formats must honor the same section-visibility and sensitivity policy.

## 9. Edit + View Combined Rules

These rules prevent edit and view policy from diverging in confusing ways.

### Rule A

If a field is hidden by view policy, no edit affordance may be rendered.

### Rule B

If a field is visible but belongs to Tier 1 or Tier 4, only read-only styling may appear.

### Rule C

If a field belongs to Tier 2:

- the viewer may see the field value
- but editing must be rendered as `request change`, not direct mutation

### Rule D

If a field belongs to Tier 3:

- direct edit is allowed only in contexts where the viewer is allowed to edit that employee's data
- default direct-edit target is `employee/self`

### Rule E

Governance visibility does not imply editability. Most governance data remains read-only even for committee users.

## 10. Default Implementation Mapping

The integrated Worker Profile implementation should map policy into these booleans:

- `visibility.coreCV`
- `visibility.talentInsights`
- `visibility.performanceInsights`
- `visibility.governanceHistory`
- `visibility.exportAvailable`

And these field-level states:

- `hidden`
- `masked`
- `read_only`
- `editable_direct`
- `editable_with_approval`

## 11. Explicit Defaults Chosen for Integration

These defaults are selected because the current package-level documents do not yet provide one consolidated matrix.

- `My Profile` remains the primary self-service profile entry point.
- `Portal Admin` can browse employee directory and open employee profile, but does not automatically receive governance history.
- `Manager` can view subordinate talent/performance summaries relevant to people management, but not committee-only rationale.
- `Talent Committee` can view governance history in committee context.
- `Tier 4` fields are always read-only, but some of them are also high-sensitivity for viewing and export.
- Detailed transactional performance artifacts such as evidence files, approval queues, and month-level realization forms stay in their native workflow modules and are not fully rendered in profile.
